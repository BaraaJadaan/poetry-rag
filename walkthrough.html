We set up the project environment using uv for fast dependency management and configured a local HuggingFace cache to keep large model weights off the primary drive.

We built a preprocessing pipeline with the following data handling rules:
• Empty Poems: Dropped entirely.
• Colloquial Poetry: The dataset explicitly tags some poems as عامي (colloquial) or شعبي. We safely dropped all of those so they don't pollute the classical search engine.
• Unlabelled / Classical Poetry: We kept everything tagged as فصيح (classical) and, crucially, we kept the 28% of the dataset that had no language tag at all (since dropping them would have thrown away massive amounts of classical poetry).
• Orphan Hemistichs: We paired up all the half-lines into verses, but we deliberately kept the odd "orphan" half-lines. Discarding them would have silently deleted real poetry from the dataset.
• Diacritics: We stripped diacritics for the search index, but kept them for the display text, meaning users can search without diacritics and still get beautiful, fully-voweled poetry back.

We tested the voyage-4-nano Q8_0 GGUF model on a small sample of verses to verify its semantic performance on Arabic. We discovered and fixed a KV cache contamination bug in llama-cpp-python by manually clearing the cache, and verified that the model successfully separates distinct semantic domains like war and love, despite a minor quantization collapse on highly stylistically similar verses from the same poet.

We built a native ReAct loop using `llama-cpp-python` to give a local Qwen 3.5 9B model access to our hybrid retriever, meter analysis, and vocabulary tools, maintaining our 100% local, air-gapped deployment constraint while avoiding heavy frameworks like LangChain.

We moved the agent from the CLI into a FastAPI backend with Server-Sent Events (SSE) for token streaming. We built a premium, RTL-aware frontend using vanilla HTML/CSS/JS, incorporating a dual-toggle architecture that lets the application seamlessly switch between local inference and the OpenRouter API without altering the core orchestration logic.

We containerized the application using a multi-stage Docker build optimized for Oracle Cloud's Always Free ARM instances. We resolved dependency conflicts by mapping OS-specific wheels in `pyproject.toml`, and deployed a `cloudflared` sidecar container to securely expose the local LLM to the public internet without configuring complex Virtual Cloud Network (VCN) firewall rules.

Having proven the 100% local, air-gapped architecture on Windows, we modified the system to dynamically toggle based on the deployment environment via `USE_OPENROUTER_EMBED` and `AGENT_MODEL_PATH`. Locally, it defaults to the Voyage semantic search and OmniCoder. On the Oracle ARM cloud deployment, it seamlessly pivots to use `qwen/qwen3-embedding-8b` via the OpenRouter API for embeddings, and `unsloth/Qwen3.5-2B-MTP-GGUF` for hyper-fast generation on the ARM CPU.

Ran an evaluation harness across 19 held-out semantic queries to measure Recall@1, Recall@5, and MRR. The evaluation laid bare two hard truths of Arabic RAG: BM25 failed entirely due to the presence of Tashkeel (diacritics) in the source text, and the local voyage-nano embedding model struggled to map Arabic semantic synonyms, resulting in a baseline 0.0% accuracy that forces a re-architecture of the embedding layer and text preprocessing.

We added MLflow-backed retrieval experiment tracking for full evaluations, recording embedding configuration, corpus/table identity, Recall@k, MRR, latency, and a JSON report. GitHub Actions now runs a deterministic LanceDB retrieval fixture and builds the Docker image on every push, keeping paid API embedding work out of the fast CI feedback loop.

Phase 4: Full Corpus Vector Embedding

We indexed the entire 3.4 million verse corpus into a local vector database. We originally attempted to use ChromaDB, but the scale and GPU write speed (256-verse batches at 317 verses/second) completely broke Chroma's background compaction thread (Failed to apply logs to the hnsw segment writer). We pivoted to LanceDB, which is built for this scale and writes directly to an on-disk columnar format without fragile compaction loops.

Key Technical Wins:

  • Deterministic Hashing: Every verse gets a deterministic SHA-256 ID, making the 3.4 million row job perfectly resumable (which saved us when the laptop died mid-run!).
  • LanceDB Pivot: Smoothly transitioned away from ChromaDB when we hit its architectural limits, landing on a much more robust backend.

Phase 5: The Hybrid Retriever

We built retriever.py, the core search engine for the RAG pipeline. It connects to LanceDB and the local Voyage GGUF model to execute searches across 3.4 million rows in under 100 milliseconds.

Search Modalities:

  • Semantic (Vector) Search: Finds verses with similar meaning, even if they share zero vocabulary.
  • Keyword (FTS/BM25) Search: Natively utilizes LanceDB's Tantivy integration for exact phrase matching.
  • Hybrid (RRF) Search: Executes both searches simultaneously and mathematically combines them using Reciprocal Rank Fusion (RRF), ensuring verses that match both the concept and the vocabulary rise to the absolute top.

Technical Implementation Steps:

  • Database Connection: Built a Python class that loads the 3.4M row LanceDB table and the local Voyage model into memory.
  • The IVF_PQ Vector Index: A naive flat search against 3.4M vectors takes several seconds per query. We built an Inverted File with Product Quantization (IVF_PQ) index over the database, clustering similar vectors together and compressing their 2048 dimensions into 64 bytes. This brought semantic search latency down to ~450 milliseconds.
  • RRF Algorithm: Instead of combining raw confidence scores, we used the standard `1 / (60 + rank)` formula to blend results purely based on their relative ranking from both engines.

Phase 6: Evaluation & The Model Upgrade

To prove the engine works, we built an evaluation dataset (Golden Set) of 19 famous verses paired with realistic semantic queries (e.g., querying "الفروسية والشجاعة وركوب الخيل في الليل" and expecting it to return Mutanabbi's "الخيل والليل والبيداء تعرفني"). We ran a test harness measuring Recall@1, Recall@5, and Mean Reciprocal Rank (MRR).

Initial Baseline (Voyage-nano):

We originally chose the voyage-4-nano-gguf model for its 100% local, air-gapped privacy and incredible speed. However, the evaluation laid bare a hard truth of Arabic RAG:

  • Keyword (FTS): 52.6% Recall@5. An excellent baseline since our queries intentionally used overlapping synonyms.
  • Semantic (Vector): 0.0% Recall. We discovered that the nano model completely lacked the deep linguistic mapping to connect Arabic synonyms when there was zero keyword overlap.
  • Hybrid (RRF): 42.1% Recall@5. Because our Semantic signal was effectively random noise, the Reciprocal Rank Fusion actually degraded the excellent Keyword signal.

The Architectural Pivot (Qwen3):

Instead of accepting the 0% semantic baseline, we used this empirical data to justify upgrading the embedding layer. We dynamically pivoted the architecture to use qwen/qwen3-embedding-8b via the OpenRouter API—a massive model specifically trained on multilingual and Arabic text.

  • The Result: Semantic Recall jumped immediately from 0% to ~90% Recall@1.
  • The Lesson: This proved that our custom hybrid RAG architecture and LanceDB vector store were fundamentally perfect. The bottleneck was entirely the local embedding model's linguistic capability.
