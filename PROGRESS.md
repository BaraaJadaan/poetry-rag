# Arabic Poetry RAG — Progress

## Goal
Build a semantic verse-finder for classical Arabic poetry (موزون) — a bilingual Arabic/English portfolio RAG project targeting AI/ML engineering roles, where a user describes an occasion or feeling in natural Arabic and gets back the most fitting classical verse with poet, era, and a plain-Arabic gloss of archaic vocabulary.

## Why this idea
Chosen over generic PDF-chat and compliance-bot clones because: (1) domain is genuinely underserved — people search for the right verse at weddings, condolences, graduations and currently get keyword search or group-chat guesses; (2) RAG confirmed as top 2026 portfolio anchor across independent hiring research; (3) Arabic NLP adds real depth and differentiation; (4) the asymmetric embedding split (embed corpus once locally, query at serving time on CPU) solves a real deployment constraint and is explainable in interviews. Fine-tuning was considered and rejected — a non-technical reviewer cannot distinguish a well-tuned model from a poorly-tuned one by reading a README.

## Friction log
- Phase 1 (Jul 22) — uv not on PowerShell PATH in agent's shell; fixed by locating it at C:\Users\braaj\AppData\Local\hermes\bin\uv.exe
- Phase 2 (Jul 29) — sys.stdout.reconfigure() fails inside Jupyter (OutStream has no reconfigure); only needed when running as a .py script in PowerShell — remove that call in notebook cells
- Phase 2 (Jul 29) — Initial comment in preprocess.py incorrectly claimed that joining sadr+ajuz with a space would reunite mid-word hemistich splits (e.g. الخَل + قَ → الخلق). It does not — the space remains. Fix: Updated `raw_index` to include both the spaced version (`sadr + " " + ajuz`) and the unspaced version (`sadr + ajuz`). If it was a split word, this reunites it perfectly for BM25. If it wasn't, it creates a harmless compound token nobody will ever search for. Zero NLP overhead.
- Phase 3 (Aug 1) — suggested repo `lm-kit/voyage-4-nano-GGUF` for GGUF download; that repo does not exist. Correct repo is `jsonMartin/voyage-4-nano-gguf` (all lowercase). Additionally, that GGUF requires a separate `voyage-4-nano-linear.pt` linear projection file to recover the correct 1024-dim → 2048-dim embedding output. Decided to implement a pure numpy/zipfile loader for the .pt file to avoid torch entirely.
- Phase 3 (Aug 2) — First sanity check run called llm.embed() once per verse sequentially; KV cache leaked across calls, causing verses [2] and [3] to produce identical vectors ([2]&[3]=1.0). All pairs involving [2] or [3] were therefore meaningless. Fix: pass all verses as a list to llm.embed() in one batch call — processes them in a fresh context.
- Phase 4 (Aug 2) — Hard power loss during full corpus embedding corrupted ChromaDB's internal pickle/HNSW files (`unsupported opcode '\0'`). Because we designed `embed_corpus.py` to use deterministic SHA-256 content hashes for document IDs, the fix was simply to delete the corrupted `chromadb` folder and restart from scratch. No need for complex DB surgery; the pipeline is fully reproducible.
- Phase 4 (Aug 3) — `llama-cpp-python` crashed with `NULL pointer access` in `decode_batch` at 27% (after ~920k verses). Root cause: batch embedding an empty string (or a string of spaces that tokenizes to 0 tokens) causes the underlying C library to fail during sequence processing. Fix: added a strict filter (`len(c["text_index"].strip()) > 1`) before embedding to drop effectively empty verses.
- Phase 4 (Aug 3) — ChromaDB compaction thread crashed at 848k vectors (`Failed to apply logs to the hnsw segment writer`). Root cause: Chroma's local backend struggles to run its WAL-to-HNSW compaction under the heavy write load of GPU batch inserts at the 2.5 million scale. Fix: Swapped the vector database to LanceDB, which writes directly to an on-disk columnar format (Lance) without a fragile background compaction loop.
- Phase 6 (Aug 4) - Semantic search evaluation returned 0% Recall@5, with verses matching lexically instead of semantically. Root cause: We explicitly passed `pooling_type=2` (CLS token) to `llama-cpp-python`, but the Voyage-4-nano base model (Qwen 3) uses Mean Pooling (`pooling_type=1`). We extracted random noise instead of the semantic embedding. Fix: Updated `embed_corpus.py` and `retriever.py` to use `pooling_type=1` (Mean Pooling) and re-embedded the corpus. Semantic recall immediately jumped to expected levels, proving the vector store was healthy.
- Phase 7 (Aug 5) - The agent hallucinated gibberish poetry instead of calling the `search_verses` tool. Root cause: The script hardcoded `chat_format="qwen"`, but we loaded an `OmniCoder-Claude` model. Even after fixing the chat format, we discovered OmniCoder outputs Claude-style XML tags (`<tool_call><function=search_verses>...`) instead of the standard OpenAI JSON that `llama-cpp-python` parses natively. Fix: Because we built a native ReAct loop instead of relying on LangChain, we retained full control. We simply added a 15-line custom Regex fallback parser in `agent.py` to catch the XML, parse the arguments, and inject them seamlessly into our execution loop.
- Phase 7 (Aug 5) - Jinja template crashed with `TypeError: Can only get item pairs from a mapping` when appending the tool response. Root cause: The OmniCoder chat template does not support OpenAI's strict `role: tool` schema. Fix: Bypassed the limitation by appending the tool output as a standard `role: user` message.
- Phase 7 (Aug 5) - Agent continued to hallucinate fake poetic meters (e.g., "المتدارم") despite strict system prompts instructing it not to guess. Root cause: Modern free verse snippets in the dataset (like "والحب الجميل") had empty meter fields, and the uncensored model ignored the prompt to fill the void. Fix: Modified the `search_verses` tool to filter out fragments (`len >= 6` words), forcing the retrieval of classical Amoudi poetry. Because classical verses have complete `poem_meter` metadata in LanceDB, the agent finally received hard data and stopped hallucinating.
- Phase 8 (Aug 6) — OpenRouter toggle returned `404 No endpoints found for anthropic/claude-3.5-sonnet`. Root cause: Anthropic retired the claude-3.5-sonnet endpoint on OpenRouter; the model ID became a dead route rather than auto-upgrading. Fix: Updated the hard-coded `model=` value in `agent.py` to `anthropic/claude-sonnet-5`, the current available Claude Sonnet on OpenRouter. Lesson: pin provider-hosted model slugs as named constants so future deprecations are a one-line update, not a debugging hunt.
- Phase 8 (Aug 6) — Switching the backend toggle had no visible feedback; users toggled and kept chatting, confused why responses still came from the old model (conversation context stays server-side across model switches). Fix: Added a pill-shaped glassmorphism toast (CSS `position: fixed`, spring `cubic-bezier` entry animation, 6-second auto-dismiss) that slides in from the top and includes an inline "تحديث الآن" button wired to `location.reload()`.
- Phase 8 (Aug 6) — OpenRouter / Qwen 3.7 streamed `<think>...</think>` inline inside `delta.content` (plain text, not a separate token stream). The frontend's turn-start state machine never advanced past turn 0, so the thinking drawer received both the reasoning and the final answer, and the answer area stayed empty. Fix: Added a real-time three-state parser (`before_think → in_think → after_think`) in `agent.py` that buffers incoming chunks with a partial-tag lookahead, emits thinking content on turn 0, sends `turn_start: 1` on `</think>`, and routes the rest to the answer area on turn 1 — no frontend changes required.
- Phase 8.2 (Aug 6) — `llama-cpp-python` wheels are OS-specific (Windows .whl vs Linux source build), causing standard `requirements.txt` to fail when containerizing for Oracle ARM. Fix: Mapped dependencies dynamically in `pyproject.toml` using PEP-508 environment markers (`sys_platform == 'linux'`).
- Phase 8.2 (Aug 6) — `localStorage` state management caused context pollution (hallucinations of past turns) when toggling between local LLM and API. Fix: Decoupled visual state from execution context, ensuring the chat resets cleanly upon backend switch.
- Phase 8.3 (Aug 6) — Needed to pivot to OpenRouter for semantic embeddings (`qwen/qwen3-embedding-8b`) due to Voyage-4-nano's poor semantic recall, but didn't want to wipe the working local Windows setup. Fix: Built a Dual-Environment Architecture. Python scripts fall back to local `llama.cpp` by default, while `docker-compose.yml` injects `USE_OPENROUTER_EMBED=true` to dynamically toggle the container to the OpenRouter embedding API and the fast `unsloth/Qwen3.5-2B-MTP-GGUF` generator.
  - Phase 8.4 (Aug 7) — Caught a critical infrastructure limit: the Oracle ARM instance provisioned only 1GB of RAM, making it impossible to run the Qwen 3.5 2B model locally inside the Docker container without an OOM crash. Fix: Pivoted to a 100% API proxy architecture for the cloud. `CLOUD_DEPLOYMENT=true` skips the GGUF model, routes queries to OpenRouter, and preserves the local/API toggle for the Windows laptop. The same 1GB limit also means full-corpus API indexing must wait for a bounded-memory indexer; the deployment guide now starts with a 1,000-verse smoke test.
- Phase 8.5 (Aug 12) — Adding MLflow to the default development environment made dependency installation fragile because its tracking stack includes large database dependencies. Fix: isolated MLflow in an explicit `mlops` dependency group, kept pytest in the normal dev group, and configured CI to run deterministic retrieval tests without installing MLflow or calling external embedding APIs.
- Phase 8.5 (Aug 12) — GitHub Actions failed during `uv sync` because the lockfile contains the Windows-only local `llama-cpp-python` wheel path, which does not exist on the Linux runner. Fix: CI uses `--no-install-package llama-cpp-python` because the retrieval fixture does not exercise the LLM; the Docker build remains responsible for installing the Linux package for deployment.
- Phase 8.5 (Aug 12) — The CI exclusion flag and optional extra were still insufficient because the absolute Windows wheel path remained in the shared `uv.lock`. Fix: removed the machine-specific wheel from project metadata entirely, kept the local-only import lazy, and documented a separate Windows `uv pip install` step. CI and Oracle now resolve only portable dependencies.
- Phase 8.6 (Aug 12) — GitHub Pages can host the HTML/CSS/JavaScript but cannot run FastAPI. Implementation is ready: the Pages workflow injects the Oracle API URL into a runtime config file, FastAPI uses a CORS allow-list through `FRONTEND_ORIGINS`, and the OpenRouter key stays server-side. The phase remains open until the public HTTPS URL and Pages deployment are completed. Tunnel choice changed from Cloudflare to ngrok (free plan, email-only signup, one permanent static domain) after Cloudflare demanded billing info even for its free tier.
- Phase 8.6 (Aug 12) — Deployment guide assumed Fedora and an ARM64/Ampere instance; the real server turned out to be Oracle Linux on x86_64 (E2.1.Micro free shape, ~668 MB usable, 8 GB swap already active, login user `opc`). Fix: rewrote the guide to detect the OS first (`cat /etc/os-release`, not `/etc/fedora-release`), install Docker from the RHEL repo (Oracle Linux is RHEL-binary-compatible; Docker has no dedicated Oracle Linux page), and drop the ARM-only assumptions. Lesson: x86_64 actually simplifies deployment — prebuilt wheels apply — and the swap section was already satisfied, so the guide now says so instead of sending me to create a second swap file.
- Phase 8.6 (Aug 12) — Second detection iteration: `cat /etc/os-release` revealed Oracle Linux **7.9**, not 8/9 — an EOL RHEL 7-based OS, and `ID_LIKE="fedora"` is exactly what led the original guide astray. Fix: guide now uses `yum` (not `dnf`), installs docker-ce 20.10.x from the frozen `centos/7` repo (Docker never shipped a `rhel/7` repo and stopped publishing el7 releases), installs Compose v2 as a standalone CLI-plugin binary because `docker-compose-plugin` rpm does not exist for el7, documents the `container-selinux` dependency fix (`ol7_optional_latest`/`ol7_addons`), and flags the OS as past vendor maintenance with a key-rotation caution. Verified the build stays light on 1 GB RAM: Phase 8.5 removed `llama-cpp-python` from server deps, so `uv sync` compiles nothing on x86_64.
- Phase 8.6 (Aug 12) — Full-corpus cloud embedding plan checked against reality in two rounds: (1) 3,449,196 verses at 4096-dim f32 would build an ~80-100 GB LanceDB table — local 2048-dim table is 39.5 GB on disk, a good yardstick. (2) `df -h` on the server showed the disk is even tighter than assumed: 39 GB root, only 19 GB free (52% used; container image takes ~2 GB more). Cost is a non-issue ($0.01/M tokens ≈ under $1 for the whole corpus); throughput is the constraint (≈56h optimistic at batch=100, worse if the 1-by-1 fallback path with backoff ever triggers). Fix decided and implemented now, before the cloud table exists: Matryoshka truncation to the first 1024 dims (Qwen3-Embedding's documented, near-lossless retrieval truncation) + float16 storage (verified against this project's LanceDB: f16 columns search correctly with an f32 query) — ~80-100 GB → ~10 GB. Applied as `vec[:1024]` + f16 cast in `embed_corpus.py` and `retriever.py`, so the smoke-test table is created in the exact final schema and nothing needs re-embedding later. Plus an IVF/PQ ANN index before any full run so queries don't brute-force GBs on a 1 GB box. If more headroom is ever needed, OCI supports online boot-volume resize (200 GB free-tier block quota).
- Phase 8.6 (Aug 13) — Dataset-reduction decision, measured before accepted. The user's proposed filters (complete two-hemistich verses only; drop `...` rows) keep 98% of the corpus — only 20.4k orphan + 51.9k ellipsis rows out of 3.45M — so they stay as a quality gate, not a size lever. The real lever is a 40-poet whitelist (classical canon + most-quoted moderns + the 19 poets the eval set quotes): 357k verses ≈ 10% of the corpus. Implemented as a streaming scan in `run_pipeline` (`poet_whitelist` + `quality_only`, with `limit` now counting *matching poems* — previously it took the first N rows, which would have embedded zero whitelisted verses), cloud-only via `POET_WHITELIST` in `embed_corpus.py`. Verified locally on the real corpus: 419,747 chunks pre-dedup (~350k post-dedup), 0 off-whitelist / 0 orphans / 0 ellipsis rows, and 18/18 golden eval verses survive. Note: the "بانت سعاد" entry, tagged to the *genre* "المدائح النبوية" rather than to a poet, was removed from `eval_set.json` (its indexed row also fails the quality filter). Bonus: the streaming scan doubles as the bounded-memory indexer foundation §10 requires — the 1,000-poem smoke test now exercises the exact production path.
- Phase 8.6 (Aug 14) — Post-deployment hardening, three separate failures found by verification, each with a one-line fix rather than a redesign: (1) older embed runs left genuine zero vectors from skipped API failures; a cleanup pass (single-shot `IN` clause on the zero ids; LanceDB `delete()` is a ~15 min full-table rewrite) dropped them, and the final +34,602-verse run finished the corpus at **355,000 rows, 0 zero vectors**; (2) the Tantivy FTS index had silently gone stale after the cloud table rebuild — keyword search returned nothing until `create_fts_index(..., replace=True)` was rerun; (3) the ngrok tunnel dropped once (HTTP 000 in the browser = tunnel down, not CORS), restored with `docker compose restart ngrok`. Lesson: verify each retrieval path (semantic, keyword, hybrid) end-to-end on the deployed table, not just one of them.
- Phase 8.6 (Aug 14) — "The answers are still shit" turned out to be TWO independent bugs, only found by a 3-query probe with `FULL_VERSE_FILTER` applied: (1) The SQL fragment filter **silently matched nothing** — stored rows carry trailing whitespace after the `***` separator, so `LIKE '%*** '` / `' ***%'` patterns never fired; fixed by TRIM()-ing inside the same three predicates (`TRIM(text_display) LIKE '%***%' AND NOT LIKE '***%' AND NOT LIKE '%***'`). (2) **Short keyword queries embed badly**: `الوحدة والشجن` anchored in the short-text cluster (30/30 fragments), while the *same corpus* answered `هجرني الأصدقاء وأصبحت وحيداً في ليل طويل` with المتنبي, أبو فراس, شوقي — the embedder was fine all along. Fix: agent prompt rule 2 now demands a full natural Arabic sentence as the search query. Commit `41da550`. Corollary: fragment rows cluster regardless of query, so retrieval-side filtering alone isn't enough — but the filter is cheap insurance for them and for the single-hemistich `أنا لست وحيداً في الدنيا ***` rows that pass verify but deserve exclusion.
- Phase 8.6 (Aug 14) — OpenRouter 429 on the shared upstream pool: two of three keys exhausted their shared-pool quota (provider_error_code `insufficient_quota`, limit_source `upstream_provider_shared_pool`) while the third worked, and the 429 surfaced mid-chat. Fix: `openrouter_failover.py` — keys are read from every `opentouter_api*` env var (the project's legacy spelling), only 429 responses trigger rotation (400/5xx are not key problems), the last key that succeeded is remembered in-process so healthy keys are tried first, and chat generation + embedding calls both retry transparently across keys — the user never sees the error. Env vars are tried in sorted name order, so the healthy key should live in `opentouter_api` to avoid a cold-start 429.

- Phase 8.6 (Aug 15) — The TRIM() fix from `41da550` did NOT work in production: LanceDB's filter pushdown runs a narrow DataFusion SQL subset and rejected it at query time — `Expression 'TRIM(text_display)' is not supported SQL in lance`, a traceback in `docker compose logs` on the first real query. Root cause chain: rows carry trailing whitespace (newline after `***`), so literal LIKE can't express "starts/ends with ***"; SQL string functions can't fix it because the engine doesn't support them. Fix: moved the predicate into Python (`is_full_verse` in retriever.py, `str.rstrip()` then contains/startswith/endswith checks) applied as a **post-filter over a wide candidate window (limit × 20)**, since the engine can't filter post-normalization. The unit test had never exercised the filter — the fix now ships a regression fixture with trailing-whitespace fragment rows. Commit `30d2663`. Lesson: validate filters against the real execution layer.
- Phase 8.6 (Aug 15) — Retrieval-quality follow-up: the sentence-query rule over-corrected. The model built a 27-word synonym pile for `حب الوطن` (`أشعر بالكبرياء والانتماء العميق لوطني ولتراث أجدادي...`) — the embedding blends every listed concept and retrieves the dominant one (فخر verses for a request about homeland love). Fix: rule 2 refined to one short sentence about a single scene/feeling, with the synonym-pile example called out as forbidden. Commit `531eedc`. Extends the `41da550` lesson: sentence-shaped AND single-focus.
- Phase 8.6 (Aug 15) — Qwen emitted the tool name `search_vverses` (doubled v) — twice. The fuzzy resolver shipped in `38b8122` handled the plain typo but the live call still failed, and the drawer showed the name typed inside Arabic RTL thinking. `3e34a12` hardened `resolve_tool` to strip everything that isn't a latin letter/underscore (backticks, bidi marks, trailing Arabic words), collapse doubled letters, then difflib-match; the raw name is logged (`[agent] raw tool call name: ...`) so a miss stays diagnosable. Prompt hardening alone was tried first and didn't stop the typo.
- Phase 8.6 (Aug 15) — Tool crashes killed the whole SSE stream: an exception inside `search_verses` (the TRIM rejection above) propagated out of the generator, the browser saw a dead connection, and the user got a bare "Connection error." — the cache also "stopped working" because failed answers were never saved. Fixes: (1) tool execution wrapped in try/except — an error becomes a tool result the model answers from, the stream survives (`47f2ca2`); (2) cache saves partial sessions when only the thinking block arrived. Lesson: an unguarded exception inside an SSE generator looks like an outage, not a bug.
