ENTRY · Core Architecture

Retrieval-Augmented Generation (RAG)

A pattern where a language model's response is grounded in documents retrieved at query time rather than relying purely on what was baked into its weights during training. The pipeline has two stages: first, a retrieval system finds the most relevant chunks from a corpus; then, a generation model uses those chunks as context to produce a final answer. The model never needs to memorise the corpus — it only needs to read and synthesise what retrieval hands it.

Why it mattered here

The Arabic poetry corpus (254k verses) is far too large and too specialised to expect any general LLM to recall correctly from weights. RAG lets us keep the corpus as a queryable index and only surface the exact verses that match a given mood or occasion — which is precisely the task.

vs. Fine-tuning

Fine-tuning bakes knowledge into the model's weights. For a portfolio project, the problem is that a non-technical reviewer cannot distinguish a well-tuned model from a poorly-tuned one by reading a README — the skill becomes invisible. RAG externalises the knowledge, making every retrieval decision legible and defensible in an interview.

ENTRY · Core Architecture

Asymmetric Retrieval

All four Voyage 4 models share one embedding space — meaning a vector produced by voyage-4-nano and one produced by voyage-4-large are directly comparable by cosine similarity. This enables a split: use a larger, slower model to embed the corpus once offline, and a smaller, faster model to embed queries at serving time. The index never needs to be rebuilt when you switch query models, because the geometry is shared.

Why it mattered here

This project embeds 254k verses once, locally, at leisure — no time pressure. At serving time, the query embedding runs on CPU on a cheap host (Render, Fly.io) that has no GPU. voyage-4-nano is small enough to run on CPU in under a second per query, which is what makes a GPU-less deployment viable. The shared embedding space is what makes this a real architecture decision rather than just using the small model everywhere.

vs. Using the same model for corpus and query

If embedding space weren't shared across model sizes, you'd be locked into whatever model you indexed with. Using nano everywhere is simpler but loses the option to upgrade corpus embedding quality later without re-indexing. The asymmetric design preserves that upgrade path at zero re-indexing cost.

ENTRY · Data

Hemistich, Sadr, Ajuz — the structure of a classical Arabic verse

A classical Arabic verse (بيت, bait) is divided into two half-lines: the sadr (صدر, "chest") and the ajuz (عجز, "tail"). Each half is called a hemistich (شطر). The split point is dictated by the poem's meter (بحر), not by word boundaries — which means the hemistich break can fall mid-word. In the Ashaar dataset, every hemistich is stored as a separate list entry, so consecutive pairs must be reunited to recover the full verse.

Why it mattered here

Embedding individual hemistichs would mean retrieving half-verses — wrong citation unit and too short for a meaningful embedding. The chunking function pairs consecutive entries (verses[0]+verses[1], verses[2]+verses[3], …) to reconstruct full baits. Poems with an odd number of hemistichs (9.57% of the corpus) get a trailing orphan chunk flagged with is_orphan=True rather than discarded, so no content is silently lost.

ENTRY · Data Cleaning

Dual-representation chunking: text_display vs. text_index

Each chunk in this pipeline carries two versions of its text. text_display preserves the original Arabic with full tashkeel (diacritics) exactly as it appears in the source — this is what users see in the UI. text_index is a normalised copy stripped of diacritics and with orthographic variants unified — this is what gets embedded and indexed. The two are generated once at chunking time and stored together in every chunk dict.

Why it mattered here

Classical Arabic poetry relies on diacritics (tashkeel) for correct pronunciation and metrical reading — stripping them from the display copy would degrade the reading experience. But a user typing on a keyboard almost never adds diacritics, so a query for كتب would fail to match كَتَبَ in a raw byte comparison. Normalising only the index copy solves both problems without trading one off against the other.

vs. Normalising a single copy used for both display and retrieval

Simpler to implement but wrong: the UI would show stripped, unvocalised text, and an interviewer asking "how do users read the returned verses" would immediately surface the problem. The extra field costs almost nothing at storage scale.

ENTRY · Data Cleaning

Arabic text normalisation for information retrieval

Arabic has several orthographic variations that create false vocabulary splits in retrieval systems: multiple spellings of alef (أ, إ, آ, ا), two forms of word-final ya (ي vs. ى), and teh marbuta (ة) which some writers render as heh (ه). Standard Arabic IR preprocessing collapses these variants and strips tashkeel (diacritics) so that أحمد, إحمد, and احمد all match the same query token. This project applies four transformations using pure Python regex and str.maketrans — no external Arabic NLP library needed at this stage.

Why it mattered here

The Ashaar corpus is fully diacriticised (مُشَكَّل), while user queries will almost never include diacritics. Without normalisation, a query for الصبر would miss الصَّبرُ entirely in BM25 and would produce noisier cosine distances for the embedding model. Applying the four standard transforms to text_index closes this gap without any external dependency or download.

ENTRY · Data Cleaning

Exclusion-list filtering vs. inclusion-list filtering

When filtering a dataset on a categorical field with multiple valid values, there are two approaches: require membership in a known "good" set (inclusion list), or reject membership in a known "bad" set (exclusion list). Inclusion filtering is stricter — anything not explicitly on the list is dropped. Exclusion filtering is more permissive — anything not explicitly on the bad list is kept, including unlabelled rows.

Why it mattered here

The poem language type field uses two different spellings for classical Arabic (فصيح at 60.4% and فصحى at 8.2%), and 28% of rows have None — which are overwhelmingly classical poems that just weren't tagged. An inclusion filter on "فصيح" alone would drop 36% of classical content. The exclusion list approach — drop عامي, شعبي, and "-" — retains everything classical (including untagged rows) while removing the 3.4% that are demonstrably colloquial.

vs. Inclusion filter on {"فصيح", "فصحى"}

Would drop the 28% null rows — a large chunk of real classical content lost because of missing labels, not because the content is wrong. Exclusion filtering is the right tool when nulls are common and the null distribution is known to be predominantly valid.

ENTRY · Embedding Sanity Check

KV cache contamination in sequential embedding

Language models maintain a key-value cache (KV cache) that stores intermediate attention computations across tokens, allowing subsequent tokens to attend to previous ones without recomputing. Embedding models reuse the same infrastructure. When you call embed() once per text string in a loop, some llama-cpp-python versions do not clear this cache between calls — so the second string's embedding is computed with leftover state from the first, producing a vector that is partly the first string's representation. In the worst case, the model just returns the cached output unchanged, giving cosine similarity of exactly 1.0 between two completely different inputs.

Why it mattered here

The first sanity check run showed [2] & [3] = 1.0000 — the war verses produced identical vectors. Every pair involving [2] or [3] was therefore meaningless. The fix is to pass all inputs as a list in a single llm.embed(list_of_texts) call, which processes them in one fresh context and avoids cross-contamination entirely.

vs. Calling reset() between embed() calls

An alternative fix is to call llm.reset() before each embed to clear the KV cache manually. Batch embedding is preferable: it's cleaner, faster (one forward pass over all inputs), and doesn't require knowing the llama-cpp-python internal API.

ENTRY · Embedding Sanity Check

Embedding sanity check — validating a model before full-corpus indexing

Before embedding a 254k-verse corpus — a process that takes hours and produces a multi-gigabyte vector store — it's worth verifying that the embedding model actually captures Arabic semantic similarity rather than just outputting high-dimensional noise. A sanity check embeds a handful of carefully chosen sentences that have known relative similarity: two verses about the same theme should score higher than two from different themes. If the similarity scores show no gradient — everything clusters at 0.95 — the model is likely outputting near-constant vectors for the language in question, and you'd catch that in minutes rather than hours.

Why it mattered here

There is no published Arabic-specific benchmark for voyage-4-nano. Rather than assume multilingual training translates to good Arabic semantic separation, we embedded 5 test verses spanning patience, war/courage, and love. The clean pairs (unaffected by the KV cache bug) showed a real gradient: patience-patience scored 0.74, patience-love scored 0.57–0.64. The model is differentiating. This is the evidence that justifies committing to full-corpus embedding.

ENTRY · Embedding Sanity Check

Q8_0 quantization collapse

8-bit quantization (Q8_0) reduces each 32-bit float weight to 8 bits, shrinking model size by ~75% with minimal quality loss for most inputs. "Most" is the key word. For inputs that are already semantically close — same poet, same meter, same high-register vocabulary — the quantization rounding can push two already-similar internal representations across a rounding boundary into the same quantized value, producing identical output vectors. Cosine similarity is then exactly 1.0, which is a red flag, not a good sign: two different sentences cannot legitimately produce the same embedding vector.

Why it mattered here

Two verses by المتنبي — one about patience, one about the sword — produced identical raw 1024-dim vectors even after explicit KV cache clearing. Replacing one with a verse by عنترة بن شداد (different poet, different era, different diction) immediately produced a distinct vector. Conclusion: the collapse is poet-style specific, not a general failure of the model. For the 254k-verse corpus, المتنبي is the most prolific contributor — this collapse rate should be monitored during full-corpus embedding, but it is not a reason to abandon Q8_0.

vs. F16 GGUF

The F16 GGUF preserves full float16 precision (identical to the original safetensors model) and eliminates quantization collapse at the cost of nearly double the file size (~695 MB vs ~372 MB). If collapse proves widespread during full-corpus embedding, switching to F16 is the fix — same repo, different filename, same loading code.

ENTRY · Embedding Sanity Check

Authorial / stylistic signal in embedding space

Embedding models trained on large multilingual corpora learn more than just thematic content — they also encode lexical style, register, and, for literary corpora, the distinctive voice of individual authors. In a similarity matrix, this shows up as same-author pairs scoring higher than cross-author pairs even when the themes differ: المتنبي's patience verse and المتنبي's sword verse scored 0.88, while patience-vs-patience across different registers (المتنبي vs. a hadith) scored only 0.74.

Why it matters for this project

For a poetry RAG system, stylistic signal is a feature. A user searching for "المتنبي's way of writing about courage" should surface both his war verses and his stoic-endurance verses — they share diction, meter, and rhetorical stance even if the nominal theme differs. What matters is that clearly different semantic domains (love vs. war) remain well-separated, and the data confirmed they do: love verses scored 0.57–0.64 against everything else, a consistent gap below the 0.73+ in-domain floor.
