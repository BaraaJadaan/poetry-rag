ENTRY · Core Architecture

Retrieval-Augmented Generation (RAG)

A pattern where a language model's response is grounded in documents retrieved at query time rather than relying purely on what was baked into its weights during training. The pipeline has two stages: first, a retrieval system finds the most relevant chunks from a corpus; then, a generation model uses those chunks as context to produce a final answer. The model never needs to memorise the corpus — it only needs to read and synthesise what retrieval hands it.

Why it mattered here

The Arabic poetry corpus (254k verses) is far too large and too specialised to expect any general LLM to recall correctly from weights. RAG lets us keep the corpus as a queryable index and only surface the exact verses that match a given mood or occasion — which is precisely the task.

vs. Fine-tuning

Fine-tuning bakes knowledge into the model's weights. For a portfolio project, the problem is that a non-technical reviewer cannot distinguish a well-tuned model from a poorly-tuned one by reading a README — the skill becomes invisible. RAG externalises the knowledge, making every retrieval decision legible and defensible in an interview.

ENTRY · Core Architecture

Asymmetric Retrieval

All four Voyage 4 models share one embedding space — meaning a vector produced by voyage-4-nano and one produced by voyage-4-large are directly comparable by cosine similarity. This enables a split: use a larger, slower model to embed the corpus once offline, and a smaller, faster model to embed queries at serving time. The index never needs to be rebuilt when you switch query models, because the geometry is shared.

Why it mattered here

This project embeds 254k verses once, locally, at leisure — no time pressure. At serving time, the query embedding runs on CPU on a cheap host (Render, Fly.io) that has no GPU. voyage-4-nano is small enough to run on CPU in under a second per query, which is what makes a GPU-less deployment viable. The shared embedding space is what makes this a real architecture decision rather than just using the small model everywhere.

vs. Using the same model for corpus and query

If embedding space weren't shared across model sizes, you'd be locked into whatever model you indexed with. Using nano everywhere is simpler but loses the option to upgrade corpus embedding quality later without re-indexing. The asymmetric design preserves that upgrade path at zero re-indexing cost.

ENTRY · Data

Hemistich, Sadr, Ajuz — the structure of a classical Arabic verse

A classical Arabic verse (بيت, bait) is divided into two half-lines: the sadr (صدر, "chest") and the ajuz (عجز, "tail"). Each half is called a hemistich (شطر). The split point is dictated by the poem's meter (بحر), not by word boundaries — which means the hemistich break can fall mid-word. In the Ashaar dataset, every hemistich is stored as a separate list entry, so consecutive pairs must be reunited to recover the full verse.

Why it mattered here

Embedding individual hemistichs would mean retrieving half-verses — wrong citation unit and too short for a meaningful embedding. The chunking function pairs consecutive entries (verses[0]+verses[1], verses[2]+verses[3], …) to reconstruct full baits. Poems with an odd number of hemistichs (9.57% of the corpus) get a trailing orphan chunk flagged with is_orphan=True rather than discarded, so no content is silently lost.

ENTRY · Data Cleaning

Dual-representation chunking: text_display vs. text_index

Each chunk in this pipeline carries two versions of its text. text_display preserves the original Arabic with full tashkeel (diacritics) exactly as it appears in the source — this is what users see in the UI. text_index is a normalised copy stripped of diacritics and with orthographic variants unified — this is what gets embedded and indexed. The two are generated once at chunking time and stored together in every chunk dict.

Why it mattered here

Classical Arabic poetry relies on diacritics (tashkeel) for correct pronunciation and metrical reading — stripping them from the display copy would degrade the reading experience. But a user typing on a keyboard almost never adds diacritics, so a query for كتب would fail to match كَتَبَ in a raw byte comparison. Normalising only the index copy solves both problems without trading one off against the other.

vs. Normalising a single copy used for both display and retrieval

Simpler to implement but wrong: the UI would show stripped, unvocalised text, and an interviewer asking "how do users read the returned verses" would immediately surface the problem. The extra field costs almost nothing at storage scale.

ENTRY · Data Cleaning

Arabic text normalisation for information retrieval

Arabic has several orthographic variations that create false vocabulary splits in retrieval systems: multiple spellings of alef (أ, إ, آ, ا), two forms of word-final ya (ي vs. ى), and teh marbuta (ة) which some writers render as heh (ه). Standard Arabic IR preprocessing collapses these variants and strips tashkeel (diacritics) so that أحمد, إحمد, and احمد all match the same query token. This project applies four transformations using pure Python regex and str.maketrans — no external Arabic NLP library needed at this stage.

Why it mattered here

The Ashaar corpus is fully diacriticised (مُشَكَّل), while user queries will almost never include diacritics. Without normalisation, a query for الصبر would miss الصَّبرُ entirely in BM25 and would produce noisier cosine distances for the embedding model. Applying the four standard transforms to text_index closes this gap without any external dependency or download.

ENTRY · Data Cleaning

Exclusion-list filtering vs. inclusion-list filtering

When filtering a dataset on a categorical field with multiple valid values, there are two approaches: require membership in a known "good" set (inclusion list), or reject membership in a known "bad" set (exclusion list). Inclusion filtering is stricter — anything not explicitly on the list is dropped. Exclusion filtering is more permissive — anything not explicitly on the bad list is kept, including unlabelled rows.

Why it mattered here

The poem language type field uses two different spellings for classical Arabic (فصيح at 60.4% and فصحى at 8.2%), and 28% of rows have None — which are overwhelmingly classical poems that just weren't tagged. An inclusion filter on "فصيح" alone would drop 36% of classical content. The exclusion list approach — drop عامي, شعبي, and "-" — retains everything classical (including untagged rows) while removing the 3.4% that are demonstrably colloquial.

vs. Inclusion filter on {"فصيح", "فصحى"}

Would drop the 28% null rows — a large chunk of real classical content lost because of missing labels, not because the content is wrong. Exclusion filtering is the right tool when nulls are common and the null distribution is known to be predominantly valid.

ENTRY · Embedding Sanity Check

KV cache contamination in sequential embedding

Language models maintain a key-value cache (KV cache) that stores intermediate attention computations across tokens, allowing subsequent tokens to attend to previous ones without recomputing. Embedding models reuse the same infrastructure. When you call embed() once per text string in a loop, some llama-cpp-python versions do not clear this cache between calls — so the second string's embedding is computed with leftover state from the first, producing a vector that is partly the first string's representation. In the worst case, the model just returns the cached output unchanged, giving cosine similarity of exactly 1.0 between two completely different inputs.

Why it mattered here

The first sanity check run showed [2] & [3] = 1.0000 — the war verses produced identical vectors. Every pair involving [2] or [3] was therefore meaningless. The fix is to pass all inputs as a list in a single llm.embed(list_of_texts) call, which processes them in one fresh context and avoids cross-contamination entirely.

vs. Calling reset() between embed() calls

An alternative fix is to call llm.reset() before each embed to clear the KV cache manually. Batch embedding is preferable: it's cleaner, faster (one forward pass over all inputs), and doesn't require knowing the llama-cpp-python internal API.

ENTRY · Embedding Sanity Check

Embedding sanity check — validating a model before full-corpus indexing

Before embedding a 254k-verse corpus — a process that takes hours and produces a multi-gigabyte vector store — it's worth verifying that the embedding model actually captures Arabic semantic similarity rather than just outputting high-dimensional noise. A sanity check embeds a handful of carefully chosen sentences that have known relative similarity: two verses about the same theme should score higher than two from different themes. If the similarity scores show no gradient — everything clusters at 0.95 — the model is likely outputting near-constant vectors for the language in question, and you'd catch that in minutes rather than hours.

Why it mattered here

There is no published Arabic-specific benchmark for voyage-4-nano. Rather than assume multilingual training translates to good Arabic semantic separation, we embedded 5 test verses spanning patience, war/courage, and love. The clean pairs (unaffected by the KV cache bug) showed a real gradient: patience-patience scored 0.74, patience-love scored 0.57–0.64. The model is differentiating. This is the evidence that justifies committing to full-corpus embedding.

ENTRY · Embedding Sanity Check

Q8_0 quantization collapse

8-bit quantization (Q8_0) reduces each 32-bit float weight to 8 bits, shrinking model size by ~75% with minimal quality loss for most inputs. "Most" is the key word. For inputs that are already semantically close — same poet, same meter, same high-register vocabulary — the quantization rounding can push two already-similar internal representations across a rounding boundary into the same quantized value, producing identical output vectors. Cosine similarity is then exactly 1.0, which is a red flag, not a good sign: two different sentences cannot legitimately produce the same embedding vector.

Why it mattered here

Two verses by المتنبي — one about patience, one about the sword — produced identical raw 1024-dim vectors even after explicit KV cache clearing. Replacing one with a verse by عنترة بن شداد (different poet, different era, different diction) immediately produced a distinct vector. Conclusion: the collapse is poet-style specific, not a general failure of the model. For the 254k-verse corpus, المتنبي is the most prolific contributor — this collapse rate should be monitored during full-corpus embedding, but it is not a reason to abandon Q8_0.

vs. F16 GGUF

The F16 GGUF preserves full float16 precision (identical to the original safetensors model) and eliminates quantization collapse at the cost of nearly double the file size (~695 MB vs ~372 MB). If collapse proves widespread during full-corpus embedding, switching to F16 is the fix — same repo, different filename, same loading code.

ENTRY · Embedding Sanity Check

Authorial / stylistic signal in embedding space

Embedding models trained on large multilingual corpora learn more than just thematic content — they also encode lexical style, register, and, for literary corpora, the distinctive voice of individual authors. In a similarity matrix, this shows up as same-author pairs scoring higher than cross-author pairs even when the themes differ: المتنبي's patience verse and المتنبي's sword verse scored 0.88, while patience-vs-patience across different registers (المتنبي vs. a hadith) scored only 0.74.

Why it matters for this project

For a poetry RAG system, stylistic signal is a feature. A user searching for "المتنبي's way of writing about courage" should surface both his war verses and his stoic-endurance verses — they share diction, meter, and rhetorical stance even if the nominal theme differs. What matters is that clearly different semantic domains (love vs. war) remain well-separated, and the data confirmed they do: love verses scored 0.57–0.64 against everything else, a consistent gap below the 0.73+ in-domain floor.

FTS / BM25 (Full Text Search)

While Vector Search finds verses by "meaning," FTS (Full Text Search) finds verses by exact keywords. BM25 is the industry-standard algorithm used inside FTS (like ElasticSearch or LanceDB's Tantivy integration). It ranks results based on how often your search words appear in the verse, adjusting for how rare those words are across the entire dataset (e.g., matching "الخيل" is worth more than matching "في").

IVF_PQ (Inverted File with Product Quantization)

A type of Vector Index used to make searching millions of vectors fast. IVF (Inverted File) clusters similar vectors together. In our dataset, we chose num_partitions=256, which runs K-Means to divide the 3.4M verses into 256 clusters (about 13,000 verses each). When searching, the engine only checks the single cluster closest to your query instead of scanning all 3.4 million verses. PQ (Product Quantization) compresses the vectors so they fit in RAM. We chose num_sub_vectors=64, which chops each 2048-dimensional vector into 64 chunks and assigns each chunk to a 1-byte lookup table. This compresses our 8-Kilobyte float vectors down to exactly 64 bytes! Together, IVF_PQ drops search latency from 5+ seconds down to milliseconds.

RRF (Reciprocal Rank Fusion)

The magic algorithm behind "Hybrid Search." If Semantic Search ranks a verse #1, and Keyword Search ranks it #3, how do you combine them? RRF assigns a score based on their rank: 1 / (constant + rank). The scores are summed up, and the highest total wins. It ensures that verses matching BOTH the meaning and the exact words rise to the absolute top, outperforming either method alone—but only if both methods return quality signals.

RAG Components: Retriever vs. Generator (Voyage vs. Qwen)

A full RAG (Retrieval-Augmented Generation) system requires two completely different AI models working together. The Retriever (e.g., Voyage-4) is an Embedding Model; it cannot talk, it only converts text into math to find relevant documents in a database. The Generator (e.g., Qwen 3.5 9b) is an LLM; it reads the documents the Retriever found and writes a natural language answer for the user. You need both: the Retriever to find the needle in the haystack, and the LLM to explain the needle.

Embedding Anisotropy (The Narrow Cone Problem)

In mathematics, cosine similarity ranges from -1 (perfect opposites) to 1 (identical), with 0 meaning completely unrelated. However, in modern LLM embeddings, vectors do not spread out evenly. They suffer from "anisotropy," meaning they all cluster into a narrow cone in the high-dimensional space. As a result, two completely unrelated sentences (e.g., "Pride in battle" vs "Eating apples") might have a similarity of 0.65 instead of 0.00. A drop from 0.90 to 0.73 might look small, but it actually spans the entire effective dynamic range of the model!

Golden Set & Evaluation Harness

How do you prove a search engine actually works? You build a Golden Set. This is a small, hand-crafted JSON file (generated via build_golden_set.py) containing realistic user queries paired with the exact verses they should return. An Evaluation Harness (our evaluate.py) then runs every query against the database and calculates metrics like Recall@5. Without this, you are just guessing if your AI is good; with it, you can mathematically prove your AI is good.

Native Tool Calling (ReAct Loop)

A technique where an LLM is given a JSON Schema describing Python functions (tools) it can call, but the application code retains full control of the execution loop. Instead of relying on a black-box framework like LangChain, the application receives a tool_calls request from the LLM, executes the local Python function, and returns the result to the LLM via a tool message role. This allows for fully transparent, debuggable agent behavior without framework bloat.

ENTRY · Deployment Architecture

Dual-Toggle LLM Architecture (Strategy Pattern)

A backend design where the core orchestration logic (the RAG pipeline and tool calling) is fully decoupled from the underlying LLM inference engine. The application reads an environment variable (or a UI toggle) to route the final generation request to either a local model (via llama-cpp-python) or a remote API (like OpenRouter). The business logic remains identical; only the text-generation executor changes.

Why it mattered here

For a portfolio project, relying purely on a third-party API hides your MLOps capability, while relying purely on a local model running on a free-tier CPU results in painfully slow responses (2-5 tokens/sec). By implementing both and switching between them seamlessly, we provide instant responses to casual web visitors via the API, while keeping the local pathway intact to prove technical competence to recruiters.

ENTRY · Deployment Architecture

Server-Sent Events (SSE) / Streaming

A unidirectional communication protocol where a web server pushes data chunks to a client over a single HTTP connection as soon as they are available, rather than waiting for the entire response to finish generating. In LLM applications, this is what allows text to appear word-by-word on the screen.

Why it mattered here

If the local model (running on an ARM CPU) takes 15 seconds to generate a complete verse explanation, making the user stare at a loading spinner for 15 seconds is a catastrophic UX failure. By streaming the tokens via SSE, the perceived latency drops to under a second, keeping the user engaged while the CPU finishes the work.

ENTRY · Frontend / API

Streaming Tag-Aware Parser (Lookahead Buffer)

When a model streams text that embeds control tags (like <think>…</think>) directly inside its token output, a naive chunk-by-chunk processor will fail: a single chunk may arrive as <th, with ink> in the next chunk. A tag-aware parser solves this by maintaining a small lookahead buffer — it withholds the last N–1 characters of each chunk (where N is the length of the longest tag you're watching for) and only emits bytes it's certain are not part of an opening or closing tag. The full parser advances through well-defined states (before_tag → in_tag → after_tag), emitting different SSE events for each region so downstream consumers can route the content to the right place without any knowledge of tags at all.

Why it mattered here

Qwen 3.7 via OpenRouter streams its chain-of-thought reasoning inside <think> tags embedded in plain delta.content — not as a separate token stream or a structured field. Without the parser, everything (reasoning and the final answer) fell into the thinking drawer as raw text. The state machine routes thinking content to the SSE turn_start: 0 channel and the answer to turn_start: 1 with zero frontend changes, because the turn_start event protocol was already the contract both sides agreed on.

vs. Post-hoc split (buffer everything, then split)

Buffering the full response and splitting after it completes works, but it destroys streaming — the user stares at a blank screen until the model finishes. The lookahead approach adds less than one token of latency while keeping real-time character-by-character rendering intact.

Concept

PEP-508 Environment Markers

When a project relies on OS-specific or architecture-specific dependencies (like a pre-compiled Windows wheel for a local GPU, but a source-compiled binary for an ARM cloud server), standard `requirements.txt` approaches fail. PEP-508 Environment Markers allow a single `pyproject.toml` to define conditional dependencies based on the host system evaluating the file at install time.

Why it mattered here

The local development environment used a hardcoded Windows `.whl` file for `llama-cpp-python` to avoid compiling C++ on Windows. But when Dockerizing the app for an Oracle ARM (Linux) server, `uv` crashed because that path did not exist in the Linux runner. The durable fix was to remove the machine-specific wheel from project metadata, keep the local import lazy, install the wheel separately on Windows, and let the portable lockfile serve CI and Linux deployment.

ENTRY · Phase 8.5: MLOps

Experiment Tracking with MLflow

Experiment tracking records the inputs and outcomes of an ML run together: the embedding model, corpus/table version, retrieval configuration, evaluation set, Recall@k, MRR, and latency. MLflow gives those runs a searchable UI and stores the metrics and JSON report as artifacts, so an improvement is evidence rather than a claim based on the latest console output.

Why it mattered here

The important experiment is not model training; it is comparing embedding and retrieval configurations for Arabic search. Keeping MLflow in the optional mlops dependency group also prevents the serving image from carrying a tracking stack it does not need.

ENTRY · Phase 8.5: MLOps

Deterministic Retrieval Regression Tests

A regression test is only useful in CI when it is fast, repeatable, and independent of paid or changing external services. The test fixture uses a tiny LanceDB table, fixed vectors, fixed queries, and known expected IDs to exercise semantic search, Tantivy full-text search, and Reciprocal Rank Fusion without calling an embedding API or rebuilding the production corpus.

Why it mattered here

The full evaluation remains available for MLflow-tracked runs, but GitHub Actions must not spend API credits or wait hours on every push. CI checks the retrieval contract itself and the Docker build; production-scale embedding is a deliberate release task.

Cross-Origin Frontend and Backend

GitHub Pages can host the project's HTML, CSS, and JavaScript, but it cannot run FastAPI or Docker. The browser therefore loads the static frontend from GitHub Pages and sends its /config and streaming /chat requests to the Oracle backend over HTTPS.

ENTRY · Phase 8.6: Static Frontend Deployment

Matryoshka Representation Learning (MRL)

A training technique that forces an embedding model to pack all of its semantic information into the leading dimensions of every vector, in order, so that truncating a 4096-dim vector down to 1024 dims loses almost no retrieval quality. "Matryoshka" is the nesting-doll name: every prefix of the vector is itself a usable embedding. The retrieval system can then store a fraction of the bytes while keeping most of the semantic power, and the same slice must be applied to query vectors too — truncating only one side would break cosine similarity between corpus and query.

Why it mattered here

The cloud corpus is 3.45M verses. At the model's default 4096 dimensions the LanceDB table would land around 80-100 GB — impossible on the Oracle free tier's real disk, which `df -h` showed to be a 39 GB root volume with only 19 GB free. Qwen3-Embedding is Matryoshka-trained, so slicing every vector to its first 1024 dims (on both the corpus and the query) shrinks the table to ~20 GB; storing float16 halves it again to ~10 GB. The slice plus the float16 cast are two small changes in the embedder and retriever, and they were made before the cloud table existed, so the smoke-test table is created in the final shape.

vs. Storing all 4096 dimensions

Full-dimension storage would make the table ~8x larger for essentially zero retrieval gain at this scale — and then slow brute-force scans at query time as well. Truncation trades a rounding-error recall loss for a 4x storage cut, float16 another 2x; storing full width only starts paying off for tasks needing extreme per-document detail, which verse retrieval does not.

ENTRY · Phase 8.6: Static Frontend Deployment

Precision-oriented corpus curation

Shrinking a retrieval corpus down to the subset that actually serves the product's users, on purpose — as a precision lever, not a shortcut. A corpus can be 98% "clean" yet still filled with rows nobody will ever search for; dropping them deliberately improves precision per query while slashing embedding time, storage, and query latency. The common mistake is reaching for completeness filters first and discovering they barely move the size dial — the real lever is deciding which rows the product serves.

Why it mattered here

All-verses indexing of 3.44M rows would take days of API calls on the free-tier VM. Measuring showed completeness filters alone keep 98% of rows (only 20k orphans + 52k ellipsis rows exist), so they're kept as a quality gate. The size lever is a 40-poet whitelist — classical canon, most-quoted moderns, and the poets the eval set quotes — landing the corpus at ~10% (350-420k verses): ~6-10 hours of embedding, ~1.5-2 GB in LanceDB, all 18 golden eval verses surviving, and no ANN index needed for acceptable query latency.

vs. Indexing everything

A full index maximizes recall breadth — any poet is searchable — but pays in days of API calls, ~10x storage, and a mandatory ANN index, while the demo experience gets dominated by obscure rows. Curation trades long-tail recall for speed, cost, and a defensible story: "we serve the canon of verses people actually quote" — which is also the product's pitch.

ENTRY · Phase 8.6: Static Frontend Deployment

Streaming pipeline over a row-ordered dataset

Processing a dataset one row at a time with an iterator instead of materializing it (or a filtered copy of it) in memory. Each row is read, checked against the active filters, kept or dropped, then discarded — peak memory stays flat no matter how many rows pass or how many total rows exist. A second subtlety: when a step carries a cap (e.g. "keep 1,000 poems"), the scan counts only rows that actually match — a dropped row must not consume budget, or a heavy filter can silently starve the output to zero.

Why it mattered here

The corpus is 254,630 poems (~3.4M verses). The pre-filtered pipeline loaded everything, which is fine on the Windows box but not on the 1 GB cloud server. The old EMBED_LIMIT also took the "first N rows of the dataset" — with the whitelist dropping most of the corpus, "first N whitelisted rows" was effectively zero. Streaming fixed both: the scan is memory-safe and the limit counts *matching* poems. It is also the pattern the bounded-memory cloud indexer needs for the full run.

ENTRY · Phase 8.6: Static Frontend Deployment

Query-phrasing sensitivity in semantic search

An embedding model maps input text to a point in a meaning space that is shaped by its training distribution. That mapping is far better conditioned for full sentences than for short abstract phrases: a complete sentence lands near other full sentences with the same meaning, while a two-word phrase can drift toward other short strings — including rows whose only virtue is being short. Retrieval quality is therefore a property of the query's phrasing, not just of the corpus or the vector store.

There is a second, opposite failure at the other extreme: a query that crams several related concepts together (الكبرياء والانتماء والعزة والفخر والشموخ والتراث) embeds as the average of everything it names, so the model retrieves whichever meaning happens to dominate that blended vector — the فخر verses came back for a request about حبّ الوطن. The reliable middle is one short sentence about a single scene or feeling, e.g. أشتاق إلى وطني وأنا بعيد عنه. The lesson in three words: short enough to be focused, sentence-shaped to anchor meaning.

Why it mattered here

With the same corpus and the same SQL filter, the two-word query الوحدة والشجن returned one-hemistich fragments (the short-text cluster), while the natural sentence هجرني الأصدقاء وأصبحت وحيداً في ليل طويل returned المتنبي, أبو فراس, and أحمد شوقي. The fix was a one-line prompt rule: the agent must phrase its search_verses query as a full Arabic sentence describing the situation or feeling. Hybrid retrieval stays because BM25 still covers the literal-token cases the semantic side is weak at.

vs. Synonym query expansion

Expanding keywords with synonyms is the classic IR answer, but it risks drifting the query away from the user's intent. A sentence-shaped query costs nothing and is evidence-backed: the probe that showed the failure also showed the sentence form succeeding against the identical corpus.

ENTRY · Phase 8.6: Static Frontend Deployment

Shared-pool rate limits and multi-key failover

OpenRouter is an aggregator: one API in front of many upstream providers. A key that is not bring-your-own-provider draws on the provider's shared pool, and when that pool's quota is exhausted the upstream answers with HTTP 429 and provider_error_code: insufficient_quota on upstream_provider_shared_pool — a per-key, not per-endpoint, condition. Multi-key failover is transparent client-side rotation: retry the identical request with the next key, rotate only on 429 (a 400 or 500 is not a key problem and will not succeed with another key), and remember which key last succeeded so healthy keys are tried first and dead ones cost exactly one failed call each.

Why it mattered here

Two of three keys were exhausted while a third worked — and the 429 surfaced mid-chat as an error the user could see. The failover module serves both chat generation and embedding calls, keys live only in server-side env vars (opentouter_api, opentouter_api2, ...), and the healthy key sits in the first variable so the container never burns a cold-start 429.

vs. Backoff-and-wait on a single key

Retrying with exponential backoff on one key is the right move when the quota is fixed, but it shares nothing between keys — if one key is dead for hours, the user waits for hours. Rotation exploits the fact that OpenRouter quotas are independent per key, turning a multi-hour outage into a few hundred milliseconds of retry.

ENTRY · Phase 8.6: Static Frontend Deployment

Storage-engine SQL filters have a narrow dialect — pre-filter vs. post-filter

Not every database can run every WHERE clause. LanceDB embeds a limited DataFusion SQL subset for filter pushdown, and it rejects things mainstream SQL takes for granted — the very first line of this project's fix crashed in production with Expression 'TRIM(text_display)' is not supported SQL in lance. "Is the predicate pushdown-supported" is therefore a real design question, not a formality.

Post-filtering is the portable fallback: fetch a deliberately wide candidate window (here limit × 20) with no pushdown, then apply the real predicate in Python and keep the top N. The wide window preserves recall — filtering after a too-tight fetch silently starves the results. It costs more work per query but works on any store, and it lets you normalize data the engine cannot (e.g. rstrip() trailing whitespace that defeats literal LIKE patterns).

Why it mattered here

Rows carry a trailing newline after the *** hemistich separator, so exact LIKE patterns about where *** begins and ends silently matched every row. The fix — TRIM() in SQL — compiled fine in unit tests but was rejected by the real engine at query time. The shipped solution normalizes in pandas (str.rstrip()) and applies the predicate as a Python function (is_full_verse) over the candidate window. The regression that would have caught this only tests the search path — the filter itself was validated against the wrong execution layer.

ENTRY · Phase 8.6: Static Frontend Deployment

LLM tool calls are untrusted input — normalize, guard, never die

A model's tool call is generated text on its way to being JSON, not trusted code dispatch: names get misspelled (search_vverses), wrapped in backticks, dotted with bidi control characters and trailing Arabic words (the name is typed inside RTL thinking), and the arguments can be malformed JSON. Treating function.name as a dictionary key without ceremony is a one-line bug. Defenses: normalize the name before lookup (strip anything that isn't a latin letter or underscore, collapse doubled letters, fuzzy-match against known tools), log the raw name for diagnosis, and wrap execution so any tool error becomes a message back to the model instead of killing the request.

Why it mattered here

Qwen emitted search_vverses twice on the live chat. Without the fuzzy resolver the whole turn degraded into an apology. And the deeper lesson came from the failure mode it hides: an unguarded exception inside a tool call used to kill the SSE stream mid-flight — the browser sees a dead connection ("Connection error.") instead of an error it could display. Tools execute inside a guarded block now, so a crash surfaces as a tool result the model can answer gracefully, and the stream never dies from a search bug.

vs. Retrying until the model names the tool correctly

We tried prompt hardening first — the model still misspelled it. Cheap, forgiving dispatch is strictly better than fighting generation variance: it fixes the hostile cases (bidi marks, backticks) a prompt can never fully prevent, and the raw-name log keeps diagnosis possible when nothing matches.
