General

Why RAG and not fine-tuning for this project?

RAG externalises the knowledge so every retrieval decision is legible; fine-tuning buries it in weights where it's invisible. For a portfolio project specifically, a non-technical reviewer cannot distinguish a well-tuned model from a poorly-tuned one by reading a README — the technical skill becomes invisible to the exact audience that matters.

The honest tradeoff: RAG requires a retrieval system to be built and maintained, and its quality ceiling is bounded by what's in the corpus. Fine-tuning can generalise beyond the corpus and can be faster at inference. But for a 254k-verse index where the task is precise verse-level recall — not generating new text in the style of classical poetry — the retrieval approach matches the problem shape better.

Technical Decision

Why voyage-4-nano instead of a larger model, or an open-weight model like nomic-embed?

Two reasons that are specific to this project, not generic "it's fast."

First, all four Voyage 4 models share one embedding space. That means the corpus can be embedded once with nano and the query embedding can be swapped to a larger model later — without re-indexing. The index is permanent; the query model is interchangeable. That's the asymmetric retrieval property, and it's what makes the deployment economics work: corpus embedding happens once locally; query embedding at serving time must run on CPU on a GPU-less host, where nano is fast enough.

Second, there is no Arabic-specific benchmark number for voyage-4-nano. Rather than assume multilingual support translates to good Arabic performance, the plan is to sanity-check it empirically on a small sample — embed ~15–20 verses, confirm thematically similar ones cluster — before committing the full corpus. That validation step is the right answer for "how did you verify model choice" in an interview.

The honest limit: nomic-embed-text is fully open-weight and runs locally for free. If the manual sanity check showed voyage-4-nano clustering poorly on Arabic, nomic would be the first alternative to test.

Technical Decision

Why Chroma or LanceDB instead of Pinecone or Qdrant?

Both Chroma and LanceDB run in-process — no server to stand up, no managed service to pay for, no Docker container to keep running. For a portfolio project with a single-developer deployment target, operational overhead is a real cost, and an in-process store eliminates it entirely.

The honest limit: in-process stores don't scale horizontally. A real production system at millions of queries would graduate to Qdrant (self-hosted, strong performance/cost) or Pinecone (fully managed, easiest ops). Both are worth knowing by name. The choice here is explicitly right-sized to portfolio scope, not production scale — and saying that clearly in an interview is a stronger answer than pretending in-process scales forever.

Technical Decision

Why is a full verse (bait) the chunking unit, rather than a hemistich or a full poem?

The retrieval unit should match the citation unit. Users ask for "a verse about patience" — they want a bait (صدر + عجز), the complete unit of classical Arabic poetry that expresses a single complete thought. That's what gets cited, shared, and attributed.

A hemistich (half-verse) is too short — it's half a thought, and often grammatically incomplete. A full poem is too long — the embedding would average across many themes and the query would compete against the poem's dominant topic rather than its individual verses. The bait is the natural granularity for both semantic meaning and user expectation.

The honest complication: the Ashaar dataset stores hemistichs as individual list entries, so the chunking function has to pair consecutive entries. 9.57% of poems have an odd number of hemistichs — those get an orphan chunk flagged with is_orphan=True rather than discarded, so content isn't silently lost.

Technical Decision

Why does each chunk store both text_display and text_index instead of just one copy?

They serve different masters. text_display is shown to the user — it must preserve full tashkeel (diacritics) because classical Arabic poetry is recited, and diacritics carry pronunciation and metrical information that plain text loses. text_index is what gets embedded and fed to BM25 — it must be normalised so that a query typed without diacritics (which is how virtually everyone types Arabic on a keyboard) matches the diacriticised corpus.

If you normalise the single copy, you break the display. If you don't normalise, you break retrieval. Two fields, generated once at chunking time, resolves both without any runtime cost.

Trick Question

You strip diacritics for retrieval — doesn't that lose meaning? In Arabic, كَتَبَ (he wrote) and كُتِبَ (it was written) differ only in diacritics.

Common misconception

Conflating "normalise for retrieval" with "permanently destroy the distinction." The diacritics are lost only from text_index — the retrieval copy. text_display retains them fully. When a verse is retrieved and shown to the user, the full diacriticised form is what they see.

The retrieval accuracy tradeoff is real but asymmetric: without stripping, a user querying كتب would miss every verse containing كَتَبَ. That's a false negative that degrades recall. With stripping, both كَتَبَ and كُتِبَ become كتب in the index, so a query for one retrieves the other — a very slight increase in false positives that the reranking stage can handle. The net effect is strongly positive for recall, which is the right priority in a verse-finding context where missing a good verse is worse than surfacing a slightly imprecise one.

Technical Decision

Why use an exclusion list to filter for classical Arabic, rather than an inclusion list?

Because 28% of the corpus has a null language type — and that null population is overwhelmingly classical poetry that simply wasn't tagged, not colloquial poetry that was mislabelled. An inclusion filter (keep only فصيح and فصحى) would discard 28% of valid classical content because of missing labels, not because of anything wrong with the poems.

The exclusion approach — drop عامي (colloquial dialect), شعبي (folk), and "-" (placeholder) — removes the 3.4% that are demonstrably not classical while keeping everything else, including the untagged rows. This is the right tool when nulls are common and their distribution is known (verified by spot-checking) to be valid.

The honest caveat: if the null rows contain a meaningful fraction of colloquial poetry that wasn't labelled, this filter would miss them. That's a known risk, acceptable at portfolio scale, and worth noting in the README.

Trick Question

The hemistich boundary can split a word mid-syllable. Don't you need to fix that before embedding?

Common misconception

Assuming that word-level tokenisation matters to a transformer-based embedding model the way it matters to BM25.

voyage-4-nano (and virtually every modern embedding model) uses subword tokenisation — the vocabulary operates at the character-n-gram or byte-pair-encoding level, not at whitespace-delimited words. A split like الخَل + قَ (from الخلق, "creation") becomes two adjacent subword tokens in the model's input. The model has seen split forms in multilingual pretraining and handles them without reconstruction. So for embedding, the mid-word split is not a problem in practice.

For BM25, however, it is a real problem — BM25 is exact-match on whitespace-delimited tokens. الخل ق will not match a query for الخلق. This is a known limitation flagged for the BM25 build step, where Arabic-aware morphological tokenisation (which analyses roots and prefixes rather than splitting on spaces) will address it. The two retrieval methods need different approaches.

Trick Question

Your sanity check showed two war verses with cosine similarity of exactly 1.0. That proves the model understands Arabic war poetry perfectly, right?

Common misconception

Assuming that a similarity of 1.0 is evidence of good performance rather than a sign of a bug. Cosine similarity of exactly 1.0 means the two vectors are identical — not just similar, but the same bit-for-bit. Two different sentences cannot produce identical embeddings from a functioning model; they might produce very similar ones, but not equal ones.

In this case, the 1.0 was caused by KV cache contamination. llama-cpp-python's embed() doesn't clear the KV cache between sequential calls. The third verse contaminated the fourth verse's computation, causing the model to return the cached state rather than computing a fresh embedding. Every pair involving either verse was meaningless as a result.

The fix — passing all inputs as a list in one llm.embed(list) batch call — processes them in a fresh context and eliminates the contamination. The correct interpretation: 1.0 = bug flag, not model capability. This is worth knowing because the bug is silent — nothing crashes, the numbers just look suspiciously clean.

Technical Decision

Why did you run a sanity check before embedding the full corpus? Couldn't you just embed everything and see if the retrieval works?

Full-corpus embedding on 254k verses takes hours and produces a multi-gigabyte vector store. If the model produces near-constant vectors for Arabic — outputting similar embeddings regardless of input content — you'd discover it only after wasting that time, and you'd need to re-embed from scratch with a different model.

A sanity check with 5 carefully chosen verses takes under a minute. If thematically similar verses don't score higher than thematically unrelated ones, the model isn't capturing Arabic semantics and you switch models before committing. If they do, you have empirical evidence — not an assumption — to justify the cost of full indexing.

There's no published Arabic-specific benchmark for voyage-4-nano. The sanity check is the benchmark we designed ourselves for this task, in the time it would have taken to write one batch of embedding calls.

General

Your sanity check showed patience-patience at 0.74, but patience-war at 0.88 — patience scored more similar to war than to itself. Doesn't that mean the model failed?

The patience-war pair ([0]&[2]=0.88) involved verse [2] which was contaminated by the KV cache bug — so that number can't be trusted at all. The valid clean comparisons involving only [0], [1], and [4] showed the right direction: patience-patience (0.74) > patience-love (0.64, 0.57). The model is differentiating.

Even setting the bug aside: classical Arabic poetry is all in the same register — high formality, archaic vocabulary, metrical structure. Some baseline similarity between any two classical verses is expected, regardless of theme. What matters is whether there's a gradient between same-theme and different-theme pairs, not whether the absolute scores match intuitions built on English.

The re-run with the batch embedding fix is the actual validation. Accepting the first run's contaminated numbers as ground truth would have been the mistake.

Technical Decision

You used Q8_0 quantization. How did you verify it didn't degrade Arabic embedding quality, and what would you do if it did?

The sanity check was the verification step. After fixing a KV cache contamination bug, the raw diagnostic output showed two المتنبي verses producing bit-for-bit identical 1024-dim vectors — cosine similarity 1.0. Since two genuinely different sentences cannot produce the same embedding, this is a quantization collapse: Q8_0 rounded two already-similar representations into the same quantized value.

Replacing one المتنبي verse with a verse by عنترة بن شداد (different poet, era, and diction) immediately produced distinct vectors. Conclusion: the collapse is poet-style specific — likely triggered by المتنبي's unusually consistent high-register diction — not a general Arabic failure.

If it proved widespread during full-corpus embedding, the fix is straightforward: swap to the F16 GGUF from the same repo. Same loading code, same linear projection file, just a different filename (~695 MB vs ~372 MB). The Q8_0 README claims 0.9999 mean cosine similarity to the original — that 0.0001 gap is where collapses live, and for a 254k-verse corpus with المتنبي as the most prolific poet, it's worth monitoring.

Trick Question

Your sanity check showed المتنبي's patience verse scoring 0.88 with his sword verse — higher than patience-vs-patience (0.74). Doesn't that mean the model is confusing themes?

Common misconception

Assuming embedding similarity equals thematic similarity. Embedding models encode much more than topic — they encode lexical register, syntactic patterns, and for literary corpora, the distinctive voice of individual authors. المتنبي's patience verse and sword verse share diction (rare classical vocabulary), meter (a specific poetic bahrs), and rhetorical stance (the poet asserting dominance over fate/enemies). A hadith about patience shares the theme but nothing else.

For this project specifically, authorial signal is a feature. A user querying "شجاعة المتنبي" (المتنبي's courage) should retrieve both his war verses and his stoic-endurance verses — they express the same worldview even if the nominal subject differs. What would be a failure is if love verses clustered with war verses, and they don't: love scored 0.57–0.64 against everything, a consistent gap below the 0.73+ in-domain floor. The model is not confused; it's encoding poetry, not Wikipedia categories.

Technical Decision

How did you handle the hard power loss that corrupted the ChromaDB index mid-build? Did you have to write a recovery script?

No recovery script was needed, and that was by design. The power loss corrupted ChromaDB's local SQLite/pickle backend because a write was interrupted. Instead of trying to perform "open-heart surgery" on the HNSW index files, I simply deleted the entire `chromadb` directory and restarted the embedding script.

This was only possible because I designed the pipeline to be fully deterministic. Instead of letting ChromaDB auto-generate random UUIDs, or using fragile positional IDs (like `row_5_verse_2`), every verse's document ID is the first 32 characters of the SHA-256 hash of its normalized text. The script is inherently idempotent.

If you build stateful systems assuming they will never crash, you spend hours writing recovery logic when they inevitably do. By making the document IDs deterministic content hashes, the entire vector store became a pure function of the dataset. The "recovery plan" for a corrupted database is just deleting it and letting the pipeline rebuild it.

Technical Decision

Why did you use LanceDB instead of a more common choice like ChromaDB for your local vector store?

I actually started with ChromaDB, but I hit its architectural limits during the bulk embed phase. At 2.5 million verses, with a GPU pumping out 256-vector batches (each 2048 dimensions) extremely quickly, ChromaDB's local Rust backend couldn't keep up. It uses a SQLite Write-Ahead Log (WAL) that a background thread has to continuously compact into the actual HNSW binary index.

Under heavy write load, that compaction thread fell behind and eventually crashed with a fatal Failed to apply logs to the hnsw segment writer error, corrupting the database.

Instead of trying to throttle the GPU to accommodate the database, I swapped the database to LanceDB. LanceDB is designed for this scale—it writes vectors directly to an on-disk columnar format (Lance) without a fragile background WAL compaction loop. It handled the exact same 2.5 million row insert flawlessly and gave me the exact same metadata filtering capabilities I needed for the retrieval phase.

Technical Decision

In your evaluation harness, Hybrid search (RRF) actually underperformed pure Keyword (BM25) search. Why did you keep it, or what does that metric tell you?

Tap to reveal answer

That was the most interesting finding of the project. Hybrid search blends Semantic and Keyword results using Reciprocal Rank Fusion (RRF). Our metrics showed that our tiny semantic model (Voyage-4-nano) completely collapsed on classical Arabic poetry, essentially acting as random noise.

When RRF blends a strong signal (Keyword) with random noise (Semantic), the noise drags the good results down. It empirically proves that Hybrid search isn't magic—it only works if both underlying models are returning high-quality signals. I documented this metric to show I don't just blindly implement algorithms; I measure their actual impact on the dataset.

Technical Decision

Once you realized the local Voyage-nano model scored 0% on Semantic Recall, what was your architectural fix?

Tap to reveal answer

Instead of manually tweaking chunking logic or LanceDB settings, I used the 0% metric to prove that the bottleneck was the model's underlying linguistic capability. I dynamically swapped the embedding layer to use qwen/qwen3-embedding-8b via the OpenRouter API.

Because Qwen3 is a massive parameter model specifically trained on multilingual and Arabic text, the evaluation metric immediately jumped from 0% to ~90% Recall@1 without touching a single line of the RAG orchestration code. This proved that the RAG architecture and zero-overlap semantic evaluation set were fundamentally sound, and successfully demonstrated the value of modular, decoupled system design.

Technical Decision

How did you debug the 0% Semantic Recall? How did you know it was a pooling issue rather than just a bad model?

Tap to reveal answer

Before re-embedding 3.4 million rows, I wrote a scratch script to test the model's cosine similarity on completely unrelated concepts. I tested our baseline query ("Pride in bravery in battle") against a highly similar verse, against an opposite concept ("Cowardice and running away"), and against an unrelated domain ("I love eating apples").

Under CLS pooling, the opposite concept scored exactly the same as the similar verse (0.920). It was entirely blind to meaning. When I switched to Mean Pooling, the model correctly dropped the opposite concept's score to 0.71, and the unrelated domain to 0.63.

This also proved my understanding of Embedding Anisotropy. The true "floor" of cosine similarity for this model wasn't 0.0, but around 0.63, meaning the vectors are clustered in a narrow cone. A drop from 0.90 to 0.71 is actually a massive semantic penalty, spanning most of the model's effective dynamic range.

Technical Decision

By using Product Quantization (PQ) to compress 2048 float dimensions down to 64 bytes, aren't you losing search accuracy? Is this a standard practice?

Tap to reveal answer

Yes, PQ is a "lossy compression," so the cosine distances it calculates are approximations. However, IVF_PQ is the absolute industry gold standard (invented by FAISS) and powers every major vector database (Pinecone, LanceDB, Milvus) because the tradeoff is mandatory at scale.

To fix the accuracy loss, production systems use a two-step retrieval trick: we use the compressed PQ index in RAM to quickly fetch the top 100 approximate matches. Then, the database automatically loads the uncompressed, exact vectors from the disk for just those 100 rows, recalculates the perfect distance, and gives us the true Top 5. We get the speed of RAM with the accuracy of disk.

(Note: PQ quantizes the database output vectors, whereas Q4/Q8 GGUF quantizes the neural network's internal brain weights. Same concept of grouping similar numbers into discrete buckets, but applied to different parts of the pipeline!)

Why did you write a custom native tool calling loop instead of using LangChain or LlamaIndex for your RAG agent?

Reveal Answer

Because in a production environment, framework abstractions around LLM reasoning often become liabilities. By writing a native loop using the standard OpenAI-compatible API (via llama-cpp-python), I retained complete control over the prompt, the execution state, and the error handling.

When LangChain fails to route a query correctly, you have to dig through layers of abstraction to find the hidden prompt that caused it. With a native loop, the while loop is explicit, the JSON schemas are clear, and I can step through it in a debugger. Furthermore, relying purely on the native API makes the architecture significantly lighter and easier to deploy, especially since our core constraint was running fully local and air-gapped.

How did you handle models that didn't strictly follow the expected JSON function-calling schema?

Reveal Answer

This was one of the most interesting challenges. I tested an OmniCoder model that was fine-tuned to use Claude's XML syntax (<tool_call>) instead of OpenAI JSON. The standard llama-cpp-python parser completely failed to recognize it.

Because I built a native ReAct loop instead of relying on a framework, I had full access to the raw message content. I simply wrote a regex-based fallback parser that intercepts the XML tags, parses the function name and arguments into a standard Python dictionary, and injects it seamlessly into my execution loop. If I had been using LangChain, this would have crashed the entire agent and I would have been forced to change models.

General

You built this to be a fully local ML project, but your live deployment uses the OpenRouter API. Why the bait and switch?

It's not a bait and switch; it's a deliberate architectural toggle. The core IP of this project—the semantic chunking, the hybrid LanceDB index, the custom ReAct tool orchestration—is all custom and runs locally. However, running a 9B parameter model on a free-tier cloud CPU generates about 3 tokens per second.

In a production environment, you don't punish your users with 15-second wait times just to prove you can host weights yourself. I built the FastAPI backend using the Strategy Pattern so it can seamlessly swap the inference engine. Casual web visitors get routed to the lightning-fast OpenRouter API for a premium UX, while the exact same RAG orchestration can be run locally (or on a cloud GPU) by flipping a single environment variable.

Technical Decision

Since you deployed to a cloud server, why did you use `llama.cpp` instead of a production engine like `vLLM`?

Because of the deployment hardware constraints. My Oracle ARM instance has only 1GB of RAM and no GPU, so running the local Qwen model inside the server would be unreliable. `vLLM` is designed for high-throughput GPU serving and is not a sensible fit for this machine.

I kept `llama.cpp` for local Windows development, but the cloud container uses a lightweight API-proxy architecture: OpenRouter handles generation and query embeddings, while Docker, deterministic retrieval tests, MLflow evaluations, and the deployment workflow still belong to my system. This trades inference cost for a reliable $0 infrastructure deployment.

Technical Decision

Qwen 3.7 via OpenRouter was dumping both its internal reasoning and the final answer into the thinking drawer. How did you fix that without changing any frontend code?

The root cause was a protocol mismatch. The local model produces tool-call turns that our SSE loop converts into turn_start events, which the frontend uses to route content into either the thinking drawer (turn 0) or the answer area (turn 1). Qwen 3.7 via OpenRouter doesn't use tool-call protocol — it streams plain text and buries its reasoning inside <think>…</think> tags inline in delta.content. Because the turn index never advanced past 0, everything went into the thinking drawer raw.

The fix is a three-state streaming parser in agent.py: before_think → in_think → after_think. It maintains a small lookahead buffer across chunks to safely span tag boundaries (a single chunk might contain only <th, with the rest arriving in the next chunk). Content inside the tags is emitted as turn-0 thinking; on </think> it emits a turn_start: 1 SSE event; everything after goes to the answer area. Zero frontend changes required — the same event protocol was already there.

The lesson: any model that isn't native-tool-call will leak its reasoning into the wrong layer unless the backend explicitly parses and splits it. Don't assume all providers use the same streaming contract.

Technical Decision

Why does switching the backend toggle require a page refresh? Why not swap the model live mid-session?

The conversation history is stored as a flat JavaScript array on the client and sent with every request. If a user switches from the local model to OpenRouter mid-session, the backend receives prior assistant messages that were formatted for a completely different context window and token budget. More importantly, the system prompt and tool schema are injected server-side on the first turn — switching mid-conversation means the new model receives history that was produced under a different system prompt, which is a known cause of reasoning drift and hallucination.

A page refresh is the clean architectural solution: it clears the conversation array, re-establishes the correct system prompt for the new backend, and avoids any cross-model context contamination. Rather than silently letting users continue and experience degraded results, we added a pill-shaped glassmorphism toast that slides in from the top with a spring animation (cubic-bezier(0.34, 1.56, 0.64, 1)), names the target backend, and surfaces an inline "تحديث الآن" button wired to location.reload(). It auto-dismisses after six seconds. The UX is transparent and actionable rather than surprising.

Technical Decision

How did you implement conversation persistence across reloads without polluting the LLM's context window with its own past reasoning?

I used localStorage to cache the last 10 turns so the user doesn't lose their history on reload. However, the naive approach—pushing those cached messages directly back into the conversation array—caused severe context pollution. The model started reading its own previous tool calls and internal chain-of-thought as if they were part of the current prompt.

The fix was to decouple the visual state from the execution state. When the page loads, the frontend parses the cached JSON and dynamically creates the DOM elements to render the history visually on screen. But crucially, it leaves the underlying conversation array completely empty. This ensures the user gets a seamless visual experience, while every new chat session starts with a pristine context window and a fresh system prompt.

Technical Decision

The local model got stuck in an infinite loop calling the same search tool over and over. Why did this happen and how did you break it?

This happened because I passed sampling parameters (like temperature=0.7) to the local OmniCoder model, making it more creative. In the first pass, it successfully generated the XML tool call <function=search_verses>. The server executed the tool and appended the result to the chat history.

However, in the second pass, the uncensored model saw its own previous XML tool call in the context window and hallucinated that it needed to output the same XML string again, triggering an infinite loop of repeated tool executions. I fixed this using two guardrails: First, I added strict stop=["</tool_call>", "</function>"] sequences to the inference engine to physically cut off generation the millisecond a tool call completes. Second, I dynamically injected a strict system warning ("Do not call the tool again, just provide the answer") directly into the tool result prompt. This completely locked the model into the correct ReAct pattern.

Technical Decision
You built a hybrid evaluation pipeline (Dense + BM25) and got 0.0% Recall across the board on your first run. What went wrong, and how does this affect your architecture moving forward?

It exposed two classic pitfalls of building RAG for Arabic text that standard tutorials often miss:

1. The Diacritics (Tashkeel) Problem: BM25 looks for exact matches. The source verses were stored with heavy diacritics (e.g., الخَيْلُ), while the user queries were plain text (e.g., الخيل). Because Tantivy’s default FTS doesn't strip Arabic diacritics, it failed to find any exact keyword matches, completely neutering the Keyword retrieval side of the hybrid approach.

2. Multilingual Model Limitations: We used a small, local embedding model (voyage-4-nano-gguf). While great for English, its semantic mapping for rich Arabic poetry (matching a plain-text synopsis to the actual classical verse) was severely underpowered, meaning it pulled arbitrary snippets instead of the correct verse.

The Fix: This means we have to add a strict normalization preprocessing step (stripping all diacritics and normalizing characters like Alef and Yaa) before indexing into LanceDB, and we likely need to upgrade the embedding model to something specifically tuned for Arabic semantics, like a Qwen or specialized multilingual model.

Why track retrieval evaluations in MLflow instead of only keeping console output or CI logs?

Console output tells me what happened once; MLflow records the conditions that produced the result. For each run I log the embedding mode and model, LanceDB table, evaluation-set size, top-k, Recall@1, Recall@5, MRR, latency, and a JSON metrics artifact.

I chose local or configured MLflow tracking rather than adding a tracking server to Oracle immediately. Architecture

How does a GitHub Pages frontend communicate with your FastAPI backend on Oracle?

GitHub Pages serves only the static frontend. At build time, the Pages workflow injects the public Oracle API URL into a small runtime configuration file. The browser then sends GET /config and the POST request to /chat at that URL, and reads the backend's streaming response.

Because the domains differ, FastAPI enables CORS for only the GitHub Pages origin. I keep the OpenRouter API key in the Oracle server's environment, never in the frontend or GitHub Pages artifact.

Deployment

Why did you use an ngrok static domain instead of putting the Oracle IP and port directly in the frontend?

The frontend needs a stable HTTPS origin, but exposing the FastAPI port directly would require opening and maintaining both the Oracle network and OS firewall rules. An ngrok static domain gives the backend a permanent HTTPS hostname and keeps the origin port private; ngrok connects to the internal Docker service at http://web:8000.

I would use an ephemeral tunnel URL only for temporary testing because its random hostname can change. The static domain is the better fit for a GitHub Pages frontend whose build artifact contains a fixed backend URL.

Technical Decision

Why does CI use a small deterministic retrieval fixture instead of rebuilding the full embedding index on every push?

The full corpus requires millions of API embedding requests, so putting it in push-triggered CI would be slow, expensive, and nondeterministic. The fixture stores a few fixed vectors and expected IDs, then exercises the same semantic, BM25, and RRF code paths without external API calls.

The trade-off is that the fixture cannot prove production-scale quality. That is why it complements, rather than replaces, the full golden-set evaluation: CI catches code regressions on every push, while MLflow-tracked full runs measure model and corpus changes as deliberate experiments.

Technical Decision

Your deployment guide assumed Fedora on ARM — the server turned out to be Oracle Linux 7.9 on x86_64. How did you handle that?

I stopped assuming and started detecting: `cat /etc/os-release` on first SSH showed Oracle Linux 7.9 with `ID_LIKE="fedora"` — the exact string that had misled the original guide into the wrong install path.

Each wrong assumption had a different fix. The RHEL 7-compatible OS means `yum` instead of `dnf`, and Docker never published a `rhel/7` repo, so the install uses the frozen `centos/7` repo and the last supported 20.10.x engine line — old, but everything the compose file uses is basic. The missing `docker-compose-plugin` rpm for el7 was worked around with the standalone Compose v2 binary as a CLI plugin, keeping the `docker compose` syntax intact. The architecture being x86_64 (E2.1.Micro) was good news: standard images and prebuilt wheels, no ARM source builds. And because Oracle Linux 7 is past vendor maintenance, the box is documented as a lab environment with a key-rotation caveat rather than presented as production-safe.

The honest limitation: the guide is now specific to this exact box. A maintained OL8/9 instance would revert to the modern dnf-based install — the guide says so explicitly rather than pretending one path fits every server.

Trick Question

You embed with a 4096-dimension model — so why store only 1024 dimensions of each vector?

Common misconception: a bigger stored vector is always a more accurate one. Qwen3-Embedding is trained with Matryoshka Representation Learning, which forces all semantic information into the leading dimensions of each vector in order. Truncating to the first 1024 dims is a documented, near-lossless operation for retrieval — the model's own guidance recommends 1024 for retrieval tasks.

The real reason is storage economics: 3.45M verses at full 4096 dims would occupy roughly 80-100 GB, and `df -h` on the free-tier server showed only 19 GB free on its 39 GB root volume. Slicing to 1024 dims cuts that to ~20 GB — still borderline — so the vectors are also stored as float16 (verified working with this project's LanceDB), landing ~10 GB. The same slice must be applied to the query vector — truncating only one side would break cosine similarity between the query and the corpus entirely.

The honest limitation: truncation trades a small recall edge for a 4x storage cut. If the server ever gained real disk headroom and retrieval quality mattered more than cost, re-embedding at full width is a one-line change because corpus IDs are deterministic.

Technical Decision

Why did you index only ~350k curated verses instead of the full 3.4M-verse corpus?

Because the demo is a finder for famous poetry, not an archive — a curated subset is both a product decision and a resource decision, and the measurements made it the right call.

First I measured the cheap filters: dropping single-hemistich verses and `...`-infested rows removes only ~2% of the corpus, because the preprocessing already merges most junk at the sadr+ajuz join — so those filters stay purely as a quality gate. The real lever is a poet whitelist — the classical canon, the most-quoted moderns, and the poets the eval set quotes — which keeps ~10% (~350k deduplicated verses): ~6-10 hours of API embedding instead of 2-3 days, ~1.5-2 GB in LanceDB instead of ~10 GB, and all 18 golden eval verses survive so the Phase 6 harness still works on the cloud table.

The honest tradeoff: a full index would recall long-tail poets the whitelist cannot. I chose curation because the product targets the verses people quote at weddings and condolences — those poets are all in the list — and a fast, precise demo beats a slow, exhaustive one. The whitelist is one set constant in `embed_corpus.py`; expanding it is a one-line change, and it is a cloud-only decision — the local full-corpus index is untouched.

Trick Question

You removed a verse from your golden evaluation set — isn't that just making your tests pass?

Common misconception: shrinking an eval set to fit a change is test-cheating. That would be true if a failing case had been deleted. Here the entry was wrong before any filtering existed: it tagged "بانت سعاد" to the *genre* "المدائح النبوية", not to a poet, so the retrieval pipeline could never match it by poet metadata — and its source row also fails the new completeness filter (ellipsis/truncated text). It was a mislabeled test case, not a failing one.

The audit trail is the defense: I measured first — after curation, 18/18 of the remaining golden verses survive and are retrievable — and the removal is logged in PROGRESS.md with the reason. Nothing that could pass was deleted; the harness works unmodified against the curated cloud table.

Technical Decision

Your EMBED_LIMIT used to mean "first N rows of the dataset." Why did that break with filtering, and what did you change?

Because "first N" was resolved against the raw dataset before any filtering. Once the pipeline could drop rows (whitelist + completeness), a row-based cap silently re-interpreted itself as "first N rows that survive the filters" — and since the whitelist keeps only ~10% of the corpus, that is N *successful* whitelist matches, which in the worst case is zero poems. The smoke test would have pretended to embed "1,000 verses" while actually embedding none.

The fix came with the streaming rewrite: the scan counts only *matching* poems, so EMBED_LIMIT=1000 reliably means 1,000 whitelisted, quality-passing poems (~22k verses). Streaming additionally keeps peak memory flat over the 254,630-row crawl, which is what makes the scan runnable on the 1 GB cloud box at all.
